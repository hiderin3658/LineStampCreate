## 1. 目的・背景

外部ツール（画像生成AI等）で作成した「複数スタンプを1枚にまとめたシート画像」を入力とし、
**LINE Creators Market にそのままアップロードできる画像一式（ZIP）を自動生成する**ことを目的とする。

最終的にはこの一連の流れを **Claude Code のスキル化** し、「シート画像を渡すだけでアップロード用ZIPが出来上がる」状態を目指す。
本書はその第一歩として、スキル化の前提となる **仕様・処理フロー・技術方針** を整理するものである。

### 1.1 ゴール（段階）

| 段階 | 内容 | 本書の範囲 |
|------|------|-----------|
| Phase 1 | 仕様調査・設計書作成（＝本書） | ✅ 対象 |
| Phase 2 | 変換スクリプトの実装・1シートでの動作確認 | 設計のみ記載 |
| Phase 3 | 設定ファイルによる汎用化（複数キャラ・可変個数） | 設計のみ記載 |
| Phase 4 | Claude Code スキル化 | 構想のみ記載 |

### 2.2 実測データ（レイアウト解析の根拠）

入力画像を Python(Pillow + numpy) で解析した結果、**均等割りでは割り切れない**（1792/4=448 だが 2392/6≈398.67）一方で、
**コンテンツ間の余白（ガター）が明確に検出できる**ことを確認した。よって「固定グリッド分割」ではなく
**「余白検出によるコンテンツ駆動の分割」** を採用する根拠とする。

- 背景色: 四隅・縁とも RGB 252〜255（純白 #FFFFFF ではなくわずかにオフホワイト）→ 透過判定は **しきい値方式**（例: 各チャンネル ≧ 240）が必要。
- 縦の空白帯（列の区切り）: x ≒ 450 / 900 / 1351 付近の3本 → 4列を分離可能。
- 横の空白帯（行の区切り）: y ≒ 22 / 458 / 880 / 1283 / 1656 / 2024 付近 → 6行を分離可能。

## 3. LINE スタンプ 公式仕様（2025年版・調査結果）

出典: [LINE Creators Market ガイドライン（公式）](https://creator.line.me/ja/guideline/sticker/)

### 3.1 必要な画像

| 種類 | サイズ | 個数 | ZIP内ファイル名 |
|------|--------|------|----------------|
| メイン画像 | **240 × 240 px** | 1 | `main.png` |
| スタンプ画像 | **最大 370 × 320 px** | **8 / 16 / 24 / 32 / 40 個** から選択 | `01.png` 〜 `40.png`（連番） |
| トークルームタブ画像 | **96 × 74 px** | 1 | `tab.png` |

### 3.2 共通仕様

| 項目 | 規定 |
|------|------|
| フォーマット | PNG（すべて） |
| 解像度 | 72 dpi 以上 |
| カラーモード | RGB |
| 寸法 | **偶数 px**（自動縮小されるため） |
| 背景 | **透過必須**（イラスト等の背景は透明に） |
| 余白 | コンテンツと外枠の間に **約 10px** の余白を確保 |
| ファイルサイズ | **1画像あたり 1MB 以下** |
| ZIP合計 | **60MB 以下** |
| ファイル名 | **半角英数字**（日本語・濁点は審査エラーの原因になり得る） |

### 3.3 審査・運用上の注意

- 審査リクエスト後は **個数の変更不可**（最初に個数を確定させる）。
- LINE以外のサービス名・キャラクター名の使用禁止、宣伝目的の販売禁止 等。
- メイン画像は「セットの内容が一目で分かる代表的な絵柄」を選ぶことが推奨。

> **本プロジェクトでの確定値**: 今回のシートは 24個 構成 → **個数 = 24** で確定。

## 5. 処理パイプライン（全体フロー）

```
[入力] input/Stamp_Cat1.png （24スタンプ・白背景シート）
   │
   ▼ ① レイアウト解析
   │   余白(ガター)検出で 4列×6行 = 24セルの境界を決定
   │   （割り切れないため固定分割せず、コンテンツ駆動で分割）
   │
   ▼ ② セル分割
   │   24個のセル画像に切り出し（この時点では文字も含む＝決定事項）
   │
   ▼ ③ 背景透過（セルごと）
   │   縁から繋がった白のみを透過（フラッドフィル方式）。
   │   キャラ内部の白（毛のハイライト・白い服）は保持。＝決定事項
   │
   ▼ ④ コンテンツのトリミング
   │   透過後の不透明領域のバウンディングボックスで余白を除去
   │
   ▼ ⑤ リサイズ＆余白付与
   │   アスペクト比維持で 350×300px以内に縮小 → 余白10pxを足して
   │   最終 370×320px以内・偶数寸法に整える
   │
   ▼ ⑥ 最適化
   │   PNG(RGBA)で保存。1MB超なら減色等で圧縮し1MB以下を保証
   │
   ▼ ⑦ メイン/タブ画像生成
   │   代表スタンプ(既定=01)から 240×240 / 96×74 を生成（決定事項）
   │
   ▼ ⑧ リネーム＆ZIP化
   │   01.png〜24.png / main.png / tab.png を半角英数で命名しZIP
   │
[出力] output/Cat1/ 一式
```

## 6. 技術方針（ステップ詳細）

### ① レイアウト解析（余白検出）
- 各画素を「白に近いか（全チャンネル ≧ しきい値, 既定240）」で2値化し、非白を「コンテンツ」とみなす。
- 列方向・行方向それぞれにコンテンツ率のプロファイルを作り、**一定幅以上の低コンテンツ帯（ガター）** を区切り位置とする。
- ガター検出のしきい値（low_ratio）は既定 0.01 から始め、期待本数に満たなければ **0.02→0.03→0.05→0.08 と段階的に上げて再検出**する（効果線や装飾が薄くガターを跨ぐ場合への対策）。
- それでも期待数（列=cols-1本, 行=rows-1本）に届かない軸だけ **均等割りにフォールバック** し、警告を出す。

### ② セル分割
- 解析で得た境界でシートを 24 枚に切り出す。
- 切り出し範囲はガター中央を境界とし、各セルに少し余裕を持たせる（後段のトリミングで詰めるため切れる事故を防ぐ）。

### ③ 背景透過（フラッドフィル方式）＝採用決定
- **目的**: 単純なしきい値透過だとキャラ内部の白（毛・服）まで穴が空くため、**縁から連結した白だけ**を透過する。
- **手順**:
  1. 「白に近い」マスクを作成（しきい値方式、オフホワイト 252〜255 を吸収）。
  2. セル画像の四辺を起点に、白マスク上を **フラッドフィル（連結成分探索）** して「外側の背景白」を特定。
  3. 外側白のみ alpha=0 に。内部の白は不透明のまま残す。
  4. 境界に **1px 程度のフェザー（アンチエイリアス）** をかけ、白フチ（ハロー）を軽減。
- **パラメータ**: `threshold`(既定240), `feather`(既定1px)。絵柄により調整可能。透過方式は flood_fill 固定（設定での切替は未実装）。
- **将来オプション**: 透過が難しい絵柄向けに AI 背景除去（`rembg` 等）への切替を設定で選べるようにする（現状未導入のため Phase 2 以降で検討）。

### ③' 文字の囲み透過（自動検出）＝採用決定
- **背景**: フラッドフィルは「縁から閉じた白」を消せないため、**漢字の囲み**（`日`の中・`欲`の谷・`間`の`日`など）が白く残り、濃色のトーク背景で目立つ。販売後は画像差し替え不可のため、出力前に解消したい。
- **課題**: 囲みの白は、白い装飾（鯉のぼり・書類など）や被写体の白（猫の体・服の縞・目のハイライト）と画素単位では同じ純白で、単純な「閉じた白を全消し」では装飾を巻き込み破壊する。
- **方式（文字領域の自動検出に限定）**:
  1. 前景（不透明領域）を**連結成分**に分割。
  2. **最大成分＝被写体**として除外。残りのうち「小さく・成分の大半が暗い」もの＝**文字グリフ**とみなす（鯉・葉・書類など白/有彩オブジェクトは暗率が低く除外）。
  3. 文字グリフ内部の「縁から閉じた純白」だけを alpha=0 にし、境界を軽くフェザー。
- **パラメータ**: `text_counter_cleanup`(既定 true、setごとに無効化可)。内部既定: `white_th=244 / dark_th=150 / text_dark_frac=0.45 / max_text_ratio=0.12 / min_text_area=80`。
- **検証済み**: 漢字の囲みは透過され、白い鯉のぼり・書類・猫の目ハイライト・縞シャツ・白フチ文字は保持されることを Cat1〜3 で確認。

### ④ トリミング
- 透過後の `alpha > 0` 画素のバウンディングボックスを求め、余分な透明余白を除去。

### ⑤ リサイズ＆余白
- 余白10pxを確保するため、コンテンツを **350×300px 以内**にアスペクト比維持で縮小。
- 透明キャンバス（最終サイズ）の中央に配置。最終サイズは内容に応じて 370×320px 以内かつ **偶数**に丸める。
- 拡大はしない（元が小さい場合はそのまま中央配置）。画質劣化を避ける。

### ⑥ 最適化（1MB以下保証）
- まず PNG(RGBA, 72dpi) で保存。
- 1MBを超える場合は、(a) Pillow の最適化 → (b) 減色（256色パレット quantize, アルファ保持） の順で圧縮し1MB以下を保証。
- `pngquant` は未導入。導入できれば高品質減色が可能だが、**追加は要確認**（CLAUDE.md §3 ライブラリ無断追加禁止）。当面は Pillow 標準で実装。

### ⑦ メイン/タブ画像生成＝既存スタンプから自動生成（採用決定）
- 既定では **01番（こんにちは）** の透過済みスタンプを元に生成。代表番号は設定で変更可。
- メイン: 240×240 の透明キャンバス中央に、余白を持たせて縮小配置。
- タブ: 96×74 の透明キャンバス中央に縮小配置（横長なので顔まわり中心にトリミングする選択肢も将来検討）。

### ⑧ リネーム＆ZIP化
- スタンプを `01.png`〜`24.png`、メインを `main.png`、タブを `tab.png` に。
- これらを **同一階層**に置いた状態で ZIP 圧縮（中間フォルダを作らない）。
- ZIP が 60MB を超えないことを最終チェック。

## 7. 汎用化の設計（複数キャラ・可変個数）＝採用決定

シートごとに **設定ファイル（JSON）** を持たせ、スクリプトは設定を読んで動く構成にする。
ファイル名が `Stamp_Cat1` であることから、今後 `Cat2, Cat3…` や個数違いのシートが来る前提で汎用化する。

### 7.1 設定スキーマ（案）

```jsonc
{
  "name": "Cat1",                       // 出力フォルダ名・ZIP名に使用
  "input": "input/Stamp_Cat1.png",
  "grid": { "cols": 4, "rows": 6 },     // 余白検出で自動推定（init_config.pyが生成）
  "count": 24,                          // 8/16/24/32/40 のいずれか
  "background": {
    "mode": "white",                   // "white"(既定)=白背景から透過を生成 / "preserve"=入力の既存アルファを保持（透過処理オフ）
    "threshold": 240,
    "feather": 1,
    "text_counter_cleanup": true       // 漢字の囲み白を自動透過（既定true、無効化はfalse）
  },
  "sticker": { "max_w": 370, "max_h": 320, "margin": 10 },
  "main":  { "source_index": 5, "size": [240, 240] },                      // 代表スタンプ番号
  "tab":   { "source_index": 2, "size": [96, 74], "isolate_subject": true }, // 極小アイコン
  "max_file_kb": 1024,
  "max_zip_mb": 60
}
```

- `background.mode`（任意・既定 "white"）: `"white"` は白背景シートから透過を生成する通常モード。`"preserve"` は**入力PNGの既存アルファをそのまま使う「透過処理オフ」モード**（背景透過・囲み白除去・フェザーをスキップ）。透過済みのシートを渡すときに使う。preserve では `threshold`/`feather`/`text_counter_cleanup` は無視され、グリッド検出も白背景ではなく**アルファ（透明＝コマの隙間）基準**で行う。
- `source_index`: メイン/タブの元にするスタンプ番号（1〜count、読み順）。
- `isolate_subject`（任意・既定 false）: true にすると、そのスタンプの**最大の連結成分（＝キャラ本体）だけ**を残し、上部の文字や離れた効果線・キラキラを除去する。極小で文字が潰れるタブ画像をキャラのみにしたいときに使う。main にも指定可。
  - ⚠ 文字をキャラ頭部に重ねる構図（文字の縁取りが髪やリボンに接触）では、文字とキャラが**1つの連結成分に融合**し、isolate_subject では分離できない（最大成分が文字帯ごと残る）。この場合は次の `crop_top` を使う。
- `crop_top`（任意・既定なし・0〜1）: 元スタンプの**上部をその割合だけ切り落として**から枠に収める。文字がキャラと融合して isolate_subject が効かない絵柄で、上部の文字帯を落として**顔のクローズアップ**にしたいタブ画像向け（例: `0.3` で上から30%を除去）。main にも指定可。

> **現状の固定仕様（設定では変更しない）**: 文字はセルごと切り出して常に含める／採番は読み順（左上→右・行順）固定／背景透過は flood_fill 方式固定。透過方式の `threshold` 単純化や `rembg` 等への切替、採番順の変更は**未実装の将来オプション**。実装と乖離しないよう、これらはスキーマに載せていない。

## 9. スキル化の構想（Phase 4）

- スキル名（案）: `line-stamp-builder`
- 起動: `/line-stamp-builder input/Stamp_Cat2.png` のようにシート画像を渡す。
- スキルが行うこと:
  1. 画像を解析して個数・グリッドを推定し、設定の雛形を生成。
  2. `build_stickers.py` を実行して `output/<name>/` 一式と ZIP を生成。
  3. 生成結果（枚数・各サイズ・1MB/60MB 超過の有無）をレポート。
- 入力規約: 「白背景・グリッド配置・1キャラ・読み順採番」を前提とする（READMEに明記）。

## 10. リスク・未確定事項

| # | 項目 | 内容 | 対応方針 |
|---|------|------|---------|
| R1 | 背景透過の品質 | キャラの白い服・毛と背景白の境界が曖昧で、白フチや穴が出る可能性 | フラッドフィル＋フェザーで軽減。難ケースは rembg を提案（要確認） |
| R2 | 文字のはみ出し | 文字がセル境界に近く、分割時に切れる懸念 | ガター中央で分割＋セルに余裕を持たせる。目視確認をフローに含める |
| R3 | グリッド誤検出 | 余白が少ない絵柄で区切り検出が失敗する可能性 | 期待本数と不一致なら均等割りにフォールバック＋警告 |
| R4 | 採番順の妥当性 | 「読み順」採番がユーザー意図と異なる可能性 | 現状は読み順固定。意図と異なる場合は入力シートの並び替えで対応し、生成後に `_preview.png` で確認 |
| R5 | ライブラリ追加 | pngquant/rembg は無断追加禁止（CLAUDE.md §3） | 既存ツールで実装。必要時のみ理由を添えて確認 |
| R6 | 目視確認の必要性 | 自動処理のみでは審査落ちリスク | 生成後に 24枚サムネ＋メイン/タブのプレビューを出力し人手確認を促す |
